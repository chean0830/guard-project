# 개발 결정사항 로그

원본 기획서(`기획서.md`) 검토 후 실제 개발을 위해 확정한 사항들을 기록한다.

## 2026-09-22

1. **서류 업로드 방식**: 파일 직접 업로드 + 카메라 촬영 업로드 2가지 모두 지원.
   - 카메라 촬영 이미지는 텍스트가 아니므로 OCR이 필요 → **Google Cloud Vision API**로 처리.
   - 원본 기획서의 "OCR 불필요, 텍스트 PDF만 지원" 항목은 이 결정으로 대체됨.
   - Google Cloud 계정 및 Vision API 활성화, 서비스 계정 키 발급 필요 (사용자 직접 진행).

2. **Flutter 앱 개발 순서**: 최후순위로 미룸. 서버(Spring) + 웹(Next.js)이 안정화된 뒤 착수.

3. **공공데이터 API 승인 신청을 최우선으로 진행**. 승인 대기 시간이 있어 다른 개발과 병행하되, 신청 자체는 가장 먼저 처리.
   - 국토교통부 실거래가 API
   - 건축물대장 API
   - 도로명주소 API

4. **법적 리스크 대응**: 개인 포트폴리오 프로젝트이지만, 지적받을 여지를 없애기 위해 아래 두 문구를 반드시 화면에 노출한다.
   - **면책 문구** (결과 화면): "이 서비스는 법률 조언이 아니며 참고용 정보입니다."
   - **이용 제한 문구** (업로드 화면): "본인이 계약 당사자이거나 본인 명의로 열람 가능한 부동산에 한해 사용해주세요."
   - 두 문구 모두 실제 화면 구현 시 눈에 잘 띄는 위치(업로드 전, 결과 상단)에 배치.

5. **Git 개발 환경을 먼저 구축한 뒤 실제 코딩을 시작**한다. (`README.md`, `.gitignore`, 폴더 구조 우선 세팅)
   - GitHub 원격 저장소: https://github.com/chean0830/Project-Guard (Public)

6. **브랜치 전략: 트렁크 기반(main 단일 브랜치)**. 별도의 `develop` 브랜치는 두지 않는다.
   - 기능 단위로 짧은 브랜치(`feature/기능명`)를 만들고, 작업 후 PR을 통해 `main`에 바로 merge.
   - 이유: 1인 개발이라 `develop`/`main` 이원화(Git Flow)는 관리 부담만 늘고 실익이 없음. PR 습관은 유지해 커밋 히스토리는 깔끔하게 관리.
   - 추후 "배포 버전은 유지하면서 큰 기능을 오래 개발"해야 하는 상황이 생기면 그때 별도 브랜치 재도입 검토.

9. **위험 판단 규칙은 "근거 유형"을 셋으로 구분해서 설계**. 위험 신호 카드마다 근거 유형과 출처를 함께 표시한다.
   - `FACTUAL` (등기부 객관적 사실 그대로): 미말소 압류/가압류/경매개시결정 존재, 등기부상 소유자와 계약 상대방 불일치. 판단이 아니라 사실 확인이라 신뢰도가 가장 높음.
   - `GOVERNMENT_GUIDELINE` (정부/공공기관 권고 기준, 법적 구속력 없음): 전세가율(HUG 전세보증금 반환보증 심사 기준 참고), 선순위채권+보증금 대비 시세 비율(국토부/금감원 안내자료 참고).
   - `LAW` (법적 근거): 이번 단계에서는 규칙을 넣지 않음. 소액임차인 최우선변제금(주택임대차보호법 시행령)처럼 법적 근거가 있는 항목은 지역별 수치가 있고 개정 주기가 있어, 확인되지 않은 숫자를 하드코딩하는 대신 추후 국가법령정보센터(law.go.kr) 최신 수치로 검증 후 추가하기로 함.
   - 수치 기준(`RiskThresholds`)은 현재 상수 클래스로 관리하되, 기획서 8번 원칙(DB 기준표 관리)에 따라 추후 DB로 이전 예정.
   - "안전/위험을 법적으로 확정하지 않는다"는 기획서 원칙을 지키기 위해, 모든 규칙에 출처를 명시하고 GOVERNMENT_GUIDELINE 규칙에는 "법적 기준 아님"을 문구에 명시함.

13. **중요 버그 발견 및 수정: `me.paulschwarz:spring-dotenv:4.0.0`이 Spring Boot 4.1.1에서 `.env`를 전혀 로드하지 못하고 있었음.**
    - 증상: `@Value("${KEY:}")`로 주입되는 모든 `.env` 값(API 키, 엔드포인트 등)이 예외 없이 항상 빈 문자열로 들어옴. 등기부 파싱은 API 키가 필요 없어 정상 동작하고, 시세 조회는 조용히 실패(빈 응답)해서 "juso 테스트 DB에 인천 데이터가 없어서 null"이라는 기존 설명(11번)과 증상이 똑같이 보여 오랫동안 못 알아챈 원인.
    - 근본 원인: `spring-dotenv:4.0.0`은 `META-INF/spring.factories`로 `SpringApplicationRunListener`(`DotenvApplicationRunListener`)를 등록하는데, 이 방식 자체는 Spring Boot 4.1.1에서도 동작은 하지만 dotenv 초기화 로그(`Initialized Dotenv with ...`)가 전혀 찍히지 않는 것으로 보아 해당 리스너가 실제로 호출되지 않음을 직접 확인 (`bootRun`/devtools뿐 아니라 `bootJar`로 만든 순수 jar 실행에서도 동일하게 재현되어 devtools 문제가 아님을 배제). GitHub 저장소의 최신(main) 소스에는 Boot 4 전용 `springboot4-dotenv` 모듈이 별도로 분리되어 있는데, 아직 Maven Central에 배포되지 않은 상태 — 즉 현재 쓸 수 있는 버전(4.0.0)은 Boot 4 미지원 상태로 추정.
    - 해결: `spring-dotenv` 의존성을 제거하고, 그 내부에서 실제 파싱을 담당하던 `io.github.cdimascio:dotenv-java:3.0.0`을 직접 의존성으로 추가. `BackendApplication.main()`에서 `SpringApplication.run()` 호출 전에 `Dotenv.configure().ignoreIfMissing().load()`로 읽어 각 항목을 `System.setProperty(...)`로 등록 (시스템 프로퍼티는 Spring Environment에서 가장 우선순위가 높은 프로퍼티 소스라 어디서든 안정적으로 조회됨).
    - 수정 후 실제 아파트 시세가 정상 조회됨을 라이브로 재확인(530,000,000원 등). 이전엔 시세가 항상 null이라 `HIGH_SENIOR_DEBT_RATIO`(선순위채권비율) 규칙과 전세가율 규칙이 실질적으로 한 번도 발동한 적이 없었다는 뜻 — 이번 수정으로 실제로 작동하기 시작함.

14. **카메라 촬영 이미지 OCR(Google Cloud Vision) 연동 완료.**
    - `com.google.cloud:google-cloud-vision`(BOM `libraries-bom:26.68.0`) 추가. `RegistryImageTextExtractor`가 `DOCUMENT_TEXT_DETECTION`(표 형태로 촘촘한 문서에 적합)으로 이미지에서 텍스트를 추출.
    - 자격 증명은 Application Default Credentials(환경변수 자동 인식)에 의존하지 않고, `GOOGLE_APPLICATION_CREDENTIALS` 값을 직접 읽어 `GoogleCredentials.fromStream(...)`으로 명시적으로 로드 (ADC 자동 인식 경로는 이번 13번 버그처럼 조용히 실패할 수 있어 명시적 경로를 선호).
    - `RegistryAnalysisService.analyze(bytes, contentType)`가 `contentType`이 `image/`로 시작하면 OCR을, 아니면 기존 PDFBox 추출을 쓰도록 분기. 등기부등본 여부 검증(`NotRegistryDocumentException`, 12번 참고)은 추출 방식과 무관하게 동일하게 적용됨.
    - 실제 등기부 PDF 1페이지를 PNG로 렌더링해 업로드하는 라이브 테스트로 확인: 주소·고유번호 등 표제부 정보는 정상 인식. 다만 촬영 사진 1장에는 보통 1페이지만 담기므로, 갑구/을구가 다른 페이지에 있으면 그 페이지도 함께 업로드해야 한다는 점은 프론트엔드 UX에서 안내가 필요 (여러 장 업로드는 15번에서 구현).

15. **여러 장(페이지) 업로드 지원 + OCR 표 인식 정확도 문제 발견 및 수정.**
    - `POST /api/analyze`의 `file` 파라미터를 `files`(리스트)로 변경. `RegistryAnalysisService.analyze(List<UploadedPage>)`가 각 페이지에서 텍스트를 추출해 업로드 순서대로 이어붙인 뒤 하나의 문서로 파싱. PDF 1개짜리 업로드(`files` 크기 1)는 기존과 동일하게 동작해 하위 호환됨.
    - **문제**: 등기부 4페이지를 각각 이미지로 렌더링해 업로드했더니 갑구/을구 항목이 전부 빈 배열로 나옴. 원인 조사 결과, Vision OCR이 PDFBox와 다르게 텍스트를 뽑아냄:
      1. `【 갑 구 】`/`【 을 구 】` 같은 괄호 문구가 "갑"/"구]"처럼 서로 다른 줄로 쪼개져 나와, 한 줄 단위로 "갑구"/"을구"를 찾던 `RegistryParser`의 섹션 헤더 인식이 실패.
      2. PDFBox는 표의 한 행("1 소유권보존 ...")을 한 줄로 뽑지만, Vision은 셀 단위로 줄을 쪼개 순위번호("1")와 등기목적("소유권보존")이 서로 다른 줄에 나와, "순위번호+내용이 한 줄에 있다"고 가정한 항목 인식 규칙(`ENTRY_START`)이 매칭되지 않음.
      3. 그 여파로 "채무자"/"근저당권자" 같은 우측 컬럼 값이 원래 속한 항목이 아니라 그 뒤에 오는 다른(주로 말소) 항목 블록에 잘못 흡수되는 경우가 있음 — 이 문제는 완전히 해결하지 못해, OCR 업로드 시 일부 근저당 항목의 채무자/근저당권자 이름이 비어있을 수 있는 한계로 남음 (금액·말소여부·위험판단 결과는 PDF 업로드와 동일하게 정확함을 실제 4페이지 라이브 테스트로 확인).
    - **수정**: `RegistryParser`의 갑구/을구 헤더 판별에 항상 같이 나오는 고정 부제("소유권에 관한 사항"/"소유권 이외의 권리에 관한 사항")를 보조 기준으로 추가. `RegistryImageTextExtractor`에 OCR 결과 전용 정규화(`mergeRankNumberLines`)를 추가해, 순위번호만 단독으로 있는 줄을 다음 줄과 합쳐 PDFBox 출력과 같은 모양으로 맞춤 — PDF 경로는 전혀 건드리지 않아 회귀 위험 없음.
    - 수정 후 실제 4페이지 이미지 업로드로 재검증: 소유권/근저당(금액·말소여부)·시세·위험판단 신호(`HIGH_SENIOR_DEBT_RATIO` 포함)가 같은 문서의 PDF 업로드 결과와 사실상 동일하게 나옴을 확인.

## 2026-09-29 (2)

16. **가상 변호사 무료 상담(데모 채팅) 기능 추가 — 실제 상담 서비스가 아님을 항상 명시.**
    - 위험 신호가 발견된 사용자, 또는 이미 보증금을 못 받고 있는 사용자를 변호사 상담으로 유도하는 CTA를 메인 페이지와 분석 결과 화면(위험 신호 발견 시) 양쪽에 배치. 클릭하면 더미 변호사 10명 중 1명과 무작위 매칭되어 1:1 채팅 화면으로 이동.
    - 변호사는 전부 가상 인물(이름·소속 로펌 모두 지어낸 것, 실존 인물/법인 아님)이며, 채팅 응답도 실시간 상담이 아니라 미리 정해진 문구 3단계로만 응답한다. AI(LLM)로 변호사인 척 실시간 답변을 생성하는 방식은 선택하지 않음 — 전세사기 피해자처럼 실제로 법률 도움이 절실한 사람에게 AI가 변호사 행세를 하며 법률 조언처럼 들리는 말을 하는 것은 위험하다고 판단.
    - 화면 상단 배너와 CTA 버튼 아래에 "포트폴리오 데모이며 실제 변호사 상담이 아닙니다"라는 문구를 항상 노출하고, 실제로 도움이 필요한 경우를 위해 대한법률구조공단(국번없이 132) 연락처를 함께 안내. 기존 면책 원칙(4번, "법률 조언이 아닌 참고용 정보")과 일관성을 유지하기 위함.
