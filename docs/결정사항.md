# 개발 결정사항 로그

원본 기획서(`기획서.md`) 검토 후 실제 개발을 위해 확정한 사항들을 기록한다.

## 2026-09-22

1. **서류 업로드 방식**: 파일 직접 업로드 + 카메라 촬영 업로드 2가지 모두 지원.
   - 카메라 촬영 이미지는 텍스트가 아니므로 OCR이 필요 → **Google Cloud Vision API**로 처리.
   - 원본 기획서의 "OCR 불필요, 텍스트 PDF만 지원" 항목은 이 결정으로 대체됨.
   - Google Cloud 계정 및 Vision API 활성화, 서비스 계정 키 발급 필요 (사용자 직접 진행).

2. **Flutter 앱 개발 순서**: 최후순위로 미룸. 서버(Spring) + 웹(Next.js)이 안정화된 뒤 착수.

3. **공공데이터 API 승인 신청을 최우선으로 진행**. 승인 대기 시간이 있어 다른 개발과 병행하되, 신청 자체는 가장 먼저 처리.
   - 국토교통부 실거래가 API
   - 건축물대장 API
   - 도로명주소 API

4. **법적 리스크 대응**: 개인 포트폴리오 프로젝트이지만, 지적받을 여지를 없애기 위해 아래 두 문구를 반드시 화면에 노출한다.
   - **면책 문구** (결과 화면): "이 서비스는 법률 조언이 아니며 참고용 정보입니다."
   - **이용 제한 문구** (업로드 화면): "본인이 계약 당사자이거나 본인 명의로 열람 가능한 부동산에 한해 사용해주세요."
   - 두 문구 모두 실제 화면 구현 시 눈에 잘 띄는 위치(업로드 전, 결과 상단)에 배치.

5. **Git 개발 환경을 먼저 구축한 뒤 실제 코딩을 시작**한다. (`README.md`, `.gitignore`, 폴더 구조 우선 세팅)
   - GitHub 원격 저장소: https://github.com/chean0830/Project-Guard (Public)

6. **브랜치 전략: 트렁크 기반(main 단일 브랜치)**. 별도의 `develop` 브랜치는 두지 않는다.
   - 기능 단위로 짧은 브랜치(`feature/기능명`)를 만들고, 작업 후 PR을 통해 `main`에 바로 merge.
   - 이유: 1인 개발이라 `develop`/`main` 이원화(Git Flow)는 관리 부담만 늘고 실익이 없음. PR 습관은 유지해 커밋 히스토리는 깔끔하게 관리.
   - 추후 "배포 버전은 유지하면서 큰 기능을 오래 개발"해야 하는 상황이 생기면 그때 별도 브랜치 재도입 검토.

9. **위험 판단 규칙은 "근거 유형"을 셋으로 구분해서 설계**. 위험 신호 카드마다 근거 유형과 출처를 함께 표시한다.
   - `FACTUAL` (등기부 객관적 사실 그대로): 미말소 압류/가압류/경매개시결정 존재, 등기부상 소유자와 계약 상대방 불일치. 판단이 아니라 사실 확인이라 신뢰도가 가장 높음.
   - `GOVERNMENT_GUIDELINE` (정부/공공기관 권고 기준, 법적 구속력 없음): 전세가율(HUG 전세보증금 반환보증 심사 기준 참고), 선순위채권+보증금 대비 시세 비율(국토부/금감원 안내자료 참고).
   - `LAW` (법적 근거): 이번 단계에서는 규칙을 넣지 않음. 소액임차인 최우선변제금(주택임대차보호법 시행령)처럼 법적 근거가 있는 항목은 지역별 수치가 있고 개정 주기가 있어, 확인되지 않은 숫자를 하드코딩하는 대신 추후 국가법령정보센터(law.go.kr) 최신 수치로 검증 후 추가하기로 함.
   - 수치 기준(`RiskThresholds`)은 현재 상수 클래스로 관리하되, 기획서 8번 원칙(DB 기준표 관리)에 따라 추후 DB로 이전 예정.
   - "안전/위험을 법적으로 확정하지 않는다"는 기획서 원칙을 지키기 위해, 모든 규칙에 출처를 명시하고 GOVERNMENT_GUIDELINE 규칙에는 "법적 기준 아님"을 문구에 명시함.

13. **중요 버그 발견 및 수정: `me.paulschwarz:spring-dotenv:4.0.0`이 Spring Boot 4.1.1에서 `.env`를 전혀 로드하지 못하고 있었음.**
    - 증상: `@Value("${KEY:}")`로 주입되는 모든 `.env` 값(API 키, 엔드포인트 등)이 예외 없이 항상 빈 문자열로 들어옴. 등기부 파싱은 API 키가 필요 없어 정상 동작하고, 시세 조회는 조용히 실패(빈 응답)해서 "juso 테스트 DB에 인천 데이터가 없어서 null"이라는 기존 설명(11번)과 증상이 똑같이 보여 오랫동안 못 알아챈 원인.
    - 근본 원인: `spring-dotenv:4.0.0`은 `META-INF/spring.factories`로 `SpringApplicationRunListener`(`DotenvApplicationRunListener`)를 등록하는데, 이 방식 자체는 Spring Boot 4.1.1에서도 동작은 하지만 dotenv 초기화 로그(`Initialized Dotenv with ...`)가 전혀 찍히지 않는 것으로 보아 해당 리스너가 실제로 호출되지 않음을 직접 확인 (`bootRun`/devtools뿐 아니라 `bootJar`로 만든 순수 jar 실행에서도 동일하게 재현되어 devtools 문제가 아님을 배제). GitHub 저장소의 최신(main) 소스에는 Boot 4 전용 `springboot4-dotenv` 모듈이 별도로 분리되어 있는데, 아직 Maven Central에 배포되지 않은 상태 — 즉 현재 쓸 수 있는 버전(4.0.0)은 Boot 4 미지원 상태로 추정.
    - 해결: `spring-dotenv` 의존성을 제거하고, 그 내부에서 실제 파싱을 담당하던 `io.github.cdimascio:dotenv-java:3.0.0`을 직접 의존성으로 추가. `BackendApplication.main()`에서 `SpringApplication.run()` 호출 전에 `Dotenv.configure().ignoreIfMissing().load()`로 읽어 각 항목을 `System.setProperty(...)`로 등록 (시스템 프로퍼티는 Spring Environment에서 가장 우선순위가 높은 프로퍼티 소스라 어디서든 안정적으로 조회됨).
    - 수정 후 실제 아파트 시세가 정상 조회됨을 라이브로 재확인(530,000,000원 등). 이전엔 시세가 항상 null이라 `HIGH_SENIOR_DEBT_RATIO`(선순위채권비율) 규칙과 전세가율 규칙이 실질적으로 한 번도 발동한 적이 없었다는 뜻 — 이번 수정으로 실제로 작동하기 시작함.

21. **구글/카카오/네이버 소셜 로그인 추가.**

    - **oauth-sync 보호**: 이 엔드포인트는 로그인 자격 증명 없이 이메일만으로 세션을 발급하므로, 아무나 호출하면 임의 이메일로 로그인할 수 있는 구멍이 됨. `X-Internal-Secret` 헤더와 서버 환경변수(`INTERNAL_SYNC_SECRET`, `openssl rand -hex 32`로 생성)를 대조해 프론트엔드 서버만 호출 가능하도록 막음 — 브라우저는 이 값을 알 수 없음(프론트엔드 서버 전용 환경변수).
    - **CSRF 방지**: `/api/oauth/[provider]`에서 무작위 nonce를 만들어 httpOnly 쿠키(`oauth_state`)에 잠깐 저장하고, 로그인 후 돌아올 경로(`redirect`)도 함께 인코딩해 `state` 파라미터에 실어 보냄. 콜백에서 쿠키의 nonce와 돌아온 state의 nonce가 일치하는지 확인 후 폐기.
    - **계정 연동**: `User`에 `provider`(LOCAL/GOOGLE/KAKAO/NAVER)와 `providerId`를 추가하고 `passwordHash`는 nullable로 변경. `AuthService.oauthLogin`은 이메일로 기존 계정을 찾아 그대로 로그인시키고, 없으면 새로 만듦 — 같은 이메일로 로컬 가입 후 구글 로그인을 시도해도 같은 계정으로 합쳐짐(이메일을 신원의 기준으로 삼음). 각 provider가 이메일 제공에 동의하지 않은 경우는 로그인 실패로 처리(이메일이 곧 계정 식별자이므로 필수).
    - **에러 처리**: provider 거부, state 불일치, 이메일 미제공, 백엔드 동기화 실패 등 모든 실패 경로가 `/login?oauthError=...`로 리다이렉트되고, 로그인/회원가입 폼이 이 메시지를 사용자 문구로 보여줌.
    - 프론트엔드 `.env.example` 신설 — `OAUTH_BASE_URL`, `INTERNAL_SYNC_SECRET`(백엔드와 동일 값), provider별 client id/secret. 실제 개발용 `.env.local`은 사용자가 이미 발급해둔 세 provider 키로 채움(구글 클라우드 콘솔/카카오 디벨로퍼스/네이버 디벨로퍼스에 각각 `http://localhost:3000/api/oauth/{provider}/callback`을 리디렉션 URI로 등록해뒀다는 전제).
    - 백엔드: `AuthServiceTest`에 oauthLogin 테스트 5개(신규 생성/providerId+email 중복 방지/로컬-소셜 계정 연동/이메일 누락 시 예외), `AuthControllerTest`에 oauth-sync 테스트 2개(정상/시크릿 불일치 401) 추가, 전체 통과. 프론트엔드는 `npm run lint`/`npm run build` 통과 확인, 실제 브라우저로 로그인 페이지 버튼 노출·authorize URL 생성(client_id 포함)·에러 리다이렉트(잘못된 provider/코드·state 누락/CSRF 불일치)까지 라이브로 검증(단, 실제 provider 로그인 왕복은 브라우저 상호작용이 필요해 이번엔 수동 확인 필요 — 자동화된 라이브 테스트는 이 부분만 제외).

    - **인증**: 로그인 토큰은 httpOnly 쿠키라 브라우저가 직접 쓸 수 없으므로, Next.js 서버가 쿠키로 인증해 1회용 입장권(60초, 특정 대화방·참여자에 묶임)을 받아 넘기고 브라우저는 입장권으로만 접속한다. 허용 Origin은 `FRONTEND_ORIGIN`으로 제한. 끊기면 지수 백오프로 재연결하고, 30초 주기 조회를 안전망으로 남겼다.
    - 한계: 입장권은 서버 메모리에 보관하므로 백엔드를 여러 대로 늘리면 공유 저장소가 필요하다. 배포 시 `wss://` 사용.

30. **원하는 변호사 직접 선택 유료 기능 (토스페이먼츠).**
    - 무료 랜덤 매칭은 그대로 두고, "원하는 변호사와 매칭되고 싶어요"를 누르면 2,900원 결제 후 이용권 1장이 생긴다. 이용권이 있어야 입점 변호사 목록을 볼 수 있고, 변호사를 골라 첫 문의를 보내면 1장이 차감된다(차감과 상담 생성은 한 트랜잭션).
    - **금액은 항상 서버가 정한다**: 주문을 서버에서 먼저 만들고, 토스에서 돌아온 `amount`가 주문 금액과 다르면 승인 요청조차 하지 않는다. 같은 결제로 승인이 두 번 와도 이용권은 한 장(멱등), 주문번호를 토스 `Idempotency-Key`로도 보낸다. 시크릿 키는 백엔드 `.env`에만.
    - 개발에는 토스가 공개한 테스트 키를 쓴다(실제 결제 없음). 결제창 안의 카드 선택 화면은 자동화로 조작되지 않아, 결제창 열림·승인 경로의 오류 처리·금액 위변조 거부까지만 자동 검증했고 실제 카드 승인까지는 수동 확인.
    - **법적 검토 필요**: 변호사 매칭 대가로 돈을 받는 구조는 변호사법 제34조(알선 대가 금지) 논란이 있다. 포트폴리오 범위에서는 구현하되 실제 운영 전 검토가 필요함을 기록해 둔다.

31. **변호사 강점 프로필.** 변호사가 설정에서 한 줄 강점·경력 연차·수임료 안내·주요 실적을 직접 적고, 회원은 변호사 목록에서 이름 바로 아래로 비교한다. 관리자가 검증한 값이 아니라 변호사 본인 작성 정보라는 점을 목록에 표시하고, 입력 화면에는 확인되지 않은 승소율·과장 표현이 변호사 광고 규정에 어긋날 수 있다는 안내를 넣었다.

32. **UI 편의.** 로그인 중에는 채팅 화면을 제외한 모든 화면 위에 공통 머리글(회원/변호사/관리자별 메뉴 + 로그아웃)을 띄운다. 요청이 "로그인이 필요합니다"로 실패하면 오류 문구 대신 "로그인하시겠습니까?" 팝업을 띄우고, 로그인 후 보던 화면으로 돌려보낸다. 한글이 글자 단위로 쪼개져 줄바꿈되던 것을 `word-break: keep-all`로 띄어쓰기 기준으로 바꿨다.
    - 백엔드 테스트 179개, Playwright e2e 19개 통과.

33. **소셜 로그인을 Festlog와 분리.**
    - **원인**: 개발 PC의 Windows 사용자 환경변수에 다른 프로젝트(Festlog)의 `GOOGLE_/KAKAO_/NAVER_CLIENT_*`가 남아 있었고, 같은 값이 `.env.local`에도 복사돼 있었다. Next.js는 OS 환경변수를 `.env.local`보다 우선하므로 세 소셜 로그인 모두 Festlog 앱으로 연결되고 있었다(구글 `redirect_uri_mismatch`, 네이버 "FESTLOG에 로그인할 수 없습니다").
    - **수정**: `next.config.ts`에서 소셜 로그인·토스·내부 동기화 키는 `.env.local` 값만 쓰고, 없으면 OS 값이 있어도 비운다(백엔드 `SENSITIVE_KEYS_REQUIRING_EXPLICIT_ENV`와 같은 원칙). 키가 없는 provider는 버튼을 숨기고 로그인 시작도 막는다. 구글·카카오·네이버 모두 Project Guard 전용 앱을 새로 등록해 실제 로그인까지 확인.
    - 카카오는 Client Secret을 끌 수 있어 앱 키만 있어도 사용 가능하게 했다. 등록 과정에서 겪은 오류(KOE205 이메일 동의 권한 → 비즈 앱 전환, KOE010 시크릿 누락, KOE006 리다이렉트 URI에 경로까지 전체를 넣지 않음)는 다음 설정 때 참고용으로 남긴다.
    - 소셜 로그인 버튼에 각 사 가이드 색상과 로고(구글 G, 카카오 말풍선, 네이버 N)를 넣었고, 소셜 로그인 후 돌아갈 주소(state)도 사이트 내부 경로만 허용하도록 오픈 리다이렉트를 막았다.

34. **계정 보안 보강, 비밀번호 찾기, 결제 취소·환불, 약관.**
    - **소셜 계정 탈취 방지**: 같은 이메일이면 계정을 합치던 규칙을, 그 서비스가 이메일 소유를 확인한 경우(`emailVerified`)로 좁혔다. 구글 `email_verified`, 카카오 `is_email_verified`를 쓰고, 인증 여부를 주지 않는 네이버는 자체 메일함(`@naver.com`)만 인증된 것으로 본다. 이미 연결된 소셜 계정(provider+providerId)은 그대로 로그인되며, 인증되지 않은 이메일로 처음 들어오면 거부한다.
    - **5회 오류 잠금**: 회원·변호사는 비밀번호를 5회 연속 틀리면 맞는 비밀번호로도 로그인할 수 없고, 비밀번호 찾기(이메일 인증)로 새 비밀번호를 정해야 풀린다(사용자 요구사항). 관리자는 이메일 재설정이 없어 5회 실패 시 15분 잠금(서버 메모리).
    - **비밀번호 찾기**: 30분·1회용 재설정 링크, DB에는 SHA-256 해시만 저장. 가입 여부를 알아낼 수 없도록 없는 이메일에도 같은 응답. 재설정하면 잠금 해제와 함께 기존 세션을 모두 끊는다. 메일 설정이 없는 개발 환경에서는 링크를 서버 로그에 남긴다.
    - **결제 취소·환불**: 쓰지 않은 이용권은 회원이 즉시 결제 취소(토스 결제 취소 API), 이미 상담에 쓴 이용권은 환불 요청 → 관리자 "결제 관리" 탭에서 승인(토스 취소)/거절(사유 표시). 취소·환불 처리 중 동시 사용을 막기 위해 주문을 비관적 잠금으로 가져온다.
    - **변호사 승인/거절 메일**, **이용약관·개인정보처리방침** 페이지(대괄호 운영자 정보는 채워야 함, 정식 오픈 전 법률 검토 필요).
    - **사고와 수정**: 파일 기반 개발 DB로 바꾼 뒤 처음으로 기존 행이 있는 테이블에 NOT NULL 컬럼(`failed_login_count`, `login_locked`)을 추가하다 DDL이 실패해 서버가 뜨지 않았다. `columnDefinition`으로 DB 기본값을 줘서 해결 — 운영 DB 이전 때도 같은 문제가 생길 수 있어 기록해 둔다(이후에는 Flyway 같은 마이그레이션 도구 도입을 고려).
    - e2e는 무작위 매칭된 변호사를 신고 테스트가 잠시 정지시키는 탓에 병렬 실행 시 차단 테스트가 흔들려, 한 번에 하나씩 실행하도록 바꿨다. 백엔드 193개, e2e 19개 통과.

35. **남용 방지·탈퇴·운영 보안 보강.**
    - **등기부 분석 유료화(기존 원칙 변경)**: 기획서의 "등기부 분석은 로그인 없이 누구나" 원칙을 사용자 결정으로 바꿨다. 분석마다 유료 OCR(Google Vision)과 공공 API를 호출해 무제한 공개 시 비용 폭탄 위험이 있기 때문. 처음엔 IP당 하루 5회로 만들었다가, 사용자 요청으로 **로그인 필수 + 아이디당 무료 5회(기간 없음) → 이후 990원 분석 이용권 1회씩**으로 확정했다. 무료 횟수는 회원 ID가 아니라 이메일 해시로 세서 탈퇴 후 재가입으로 초기화되지 않는다. 무료부터 쓰고, 결제 이용권은 분석이 성공했을 때만 차감한다. 결제는 기존 이용권 구조에 상품 종류(`ProductType`: 변호사 선택 2,900원 / 분석 990원)를 더해 재사용.
    - **횟수 제한 공통화**: `RateLimitCounter`(키는 SHA-256 해시, 하루 단위와 기간 없는 누적 둘 다)로 무료 분석과 비밀번호 찾기 메일(이메일당 하루 5회, 가입 여부와 무관하게 세서 가입 여부 노출 방지)을 센다. `day`·`count`가 DB 예약어라 컬럼명을 따로 줬다.
    - **재설정 링크 로그**: 링크가 곧 계정 열쇠라, 메일 미설정 시 링크를 로그에 남기는 동작을 `LOG_RESET_LINKS=true`(개발 .env에만)일 때로 제한. 기본값은 남기지 않음 — 운영에서 메일 설정을 빠뜨려도 로그 열람자가 남의 비밀번호를 바꿀 수 없게.
    - **회원 탈퇴**: 계정·상담 대화·차단·알림 구독·세션 삭제, 결제 기록은 전자상거래법 5년 보관 의무로 유지. 미사용 이용권·검토 중 환불이 있으면 탈퇴를 막는다. 변호사 탈퇴는 진행 중 상담 처리 방식이 정해지지 않아 보류.
    - **자격 서류**: PDF·JPG만, 확장자·Content-Type이 아니라 파일 시그니처로 판별하고 저장 시 판별된 형식을 쓴다.
    - **관리자 목록**: 회원/변호사 탭 각각 20명씩 페이지 나눔과 서버 검색.
    - **운영 보안**: 보안 헤더(X-Frame-Options·frame-ancestors, nosniff, Referrer-Policy, Permissions-Policy, 운영 시 HSTS). 전체 CSP는 토스·소셜 로그인 스크립트와 맞춰야 해서 배포 환경에서 따로 적용 예정. 로그인 쿠키 7곳 모두 운영에서 `secure`. `spring.jpa.hibernate.ddl-auto`를 `DDL_AUTO` 환경변수로 분리(운영은 validate), Flyway 도입은 PostgreSQL 전환 때 함께.
    - **e2e 간헐 실패의 진짜 원인**: 처음엔 병렬 실행 탓으로 봤지만(순차 실행으로 바꿈), 실제로는 푸시 테스트가 매번 같은 이름("E2E푸시변호사")으로 변호사를 만들어 파일 DB에 동명이인이 쌓였고, 테스트들이 매칭된 변호사를 이름으로 찾다 엉뚱한 변호사로 로그인한 것이었다. 문의 응답에 `lawyerId`를 넣어 ID로 찾게 하고 테스트 변호사 이름을 매번 고유하게 바꿨다. 백엔드 202개, e2e 19개(연속 2회) 통과.

36. **회원가입 이메일 인증.**
    - **이유**: 등기부 분석을 "아이디당 무료 5회"로 바꾸자, 아무 이메일로나 계정을 계속 만들면 무료 횟수를 무한히 받을 수 있는 구멍이 생겼다(남의 이메일 선점도 가능). 이메일 가입은 6자리 인증번호를 확인해야 가입 버튼이 열린다. 소셜 로그인은 이미 인증된 이메일만 받으므로 제외, 기존 회원은 영향 없음.
    - 인증번호는 10분 유효·5회 오답 시 무효, 같은 이메일로 하루 5회까지 발송. 인증을 마치면 30분짜리 1회용 가입 토큰(해시 저장)을 받아 가입 요청에 함께 보내며, 다른 이메일로는 쓸 수 없다. 이미 가입된 이메일은 인증번호를 보내지 않는다.
    - 메일 미설정 개발 환경에서는 `LOG_VERIFICATION_CODES=true`(개발 .env에만)일 때 인증번호를 로그에 남긴다. 운영은 메일 설정(MAIL_*)이 없으면 이메일 가입 자체가 불가능하므로 배포 전 필수.
    - e2e는 인증 메일을 받을 수 없어 테스트용 회원을 `X-Internal-Secret`(oauth-sync에 쓰던 내부 비밀값)으로 인증 없이 만든다 — 이미 계정을 만들 수 있는 권한이라 새로 열리는 권한은 없다. 백엔드 207개, e2e 21개 통과, 실제 가입 화면으로 인증번호 받기→확인→가입 전 과정 확인.

37. **만료 기록 자동 정리.** 매일 새벽 4시(한국 시간)에 `ExpiredRecordCleanup`이 만료된 로그인 세션(회원·변호사·관리자), 만료 후 하루 지난 비밀번호 재설정·가입 인증 기록, 지난 날짜의 하루 단위 횟수 기록을 지운다 — 로그인할 때마다 토큰이 쌓이기만 해 DB가 계속 커지던 문제. 아이디당 무료 분석처럼 기간 없이 누적하는 횟수(`RateLimitService.LIFETIME` 날짜 줄)는 지우면 무료 횟수가 되살아나므로 명시적으로 제외했고, 이를 테스트로 고정했다. 백엔드 209개 통과.

38. **앱 관리자 콘솔과 앱 푸시 알림(FCM).**
    - **관리자 콘솔**: 웹 `/admin`과 같은 네 영역(변호사 승인·신고·회원·결제)을 아래 탭으로 옮겼다. 백엔드 API는 그대로 쓰고(관리자 인터셉터가 Bearer 토큰을 이미 받음), 자격 서류는 내려받아 임시 폴더에 저장한 뒤 기기 기본 앱(PDF 뷰어·갤러리)으로 연다(`open_filex`). 안내만 보여주던 `AccountHomeScreen`은 지웠다.
    - **웹 푸시 대신 FCM**: 24번에서 "네이티브 앱이 없어서" 웹 푸시를 골랐는데, 앱이 생겨 앱에는 FCM을 쓴다. 웹 푸시는 그대로 두고 회원에게는 웹·앱 양쪽으로, 변호사에게는 앱으로 보낸다(변호사의 웹 알림은 기존 이메일). 변호사는 새 문의와 회원 메시지 모두 받는다.
    - **토큰 저장**: `DeviceToken`(소유자 종류 USER/LAWYER + id, 토큰 unique). 같은 기기에서 다른 계정으로 로그인하면 소유자만 바꾸고, 로그아웃 직전에 앱이 해지한다. 해지는 소유자가 같을 때만 지워 남의 토큰을 지울 수 없다. 회원 탈퇴 시 함께 삭제.
    - **발송**: Firebase Admin SDK 대신 HTTP v1 API를 직접 호출한다 — Vision OCR 때문에 이미 있는 `google-auth-library`로 서비스 계정 토큰만 받으면 돼서 의존성이 늘지 않는다. 키(`FCM_CREDENTIALS_PATH`)가 없거나 발송이 실패해도 상담은 항상 성공(웹 푸시·메일과 같은 원칙), 404(UNREGISTERED)면 토큰을 지운다. OS 환경변수 섞임 방지 목록에도 추가.
    - **설정 파일이 없을 때**: `google-services.json`이 있을 때만 Gradle 플러그인을 적용하고, Firebase 초기화 실패는 잡아서 푸시만 끈다 — Firebase 프로젝트 없이도 지금처럼 빌드·실행된다(설정 파일 없이 debug APK 빌드 확인). 실제 발송은 Firebase 프로젝트를 만든 뒤 확인해야 한다.
    - 알림을 누르면 받는 사람이 지금 로그인한 계정일 때만 그 대화방을 연다. 앱을 보고 있을 때는 시스템 알림이 뜨지 않아 알림줄(SnackBar)로 보여주고, 이미 그 대화방을 보고 있으면 생략한다.
